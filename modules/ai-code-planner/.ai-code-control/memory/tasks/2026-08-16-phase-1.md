## Changes made

Sixth and largest dogfooding run of `ai-code-worker` against this repo, and the
first producing real runtime TypeScript, not documents/schemas. Plan
(`Plan/PHASE-1.md`) was a 6-task DAG, executed and merged incrementally rather than
in one shot -- each task's commit was verified and merged into `main` as soon as it
succeeded, and the plan file was trimmed to drop already-merged tasks before each
re-run, to avoid burning real Claude usage re-doing work that had already succeeded.

Two infrastructure problems solved before any task could even build:
1. `spawnSync` with `shell:false` (hardcoded in `ai-code-worker`'s
   `quality-gate.ts`) cannot resolve npm's `.cmd` wrapper on Windows -- confirmed
   directly (`ENOENT`). Verify gates invoke `node node_modules/typescript/bin/tsc`
   and `node --test ...` directly instead of `npm run build`/`npm test`.
2. Task worktrees are isolated git worktrees with no `node_modules` of their own.
   Ran `npm install` in this repo and configured every build/test gate with
   `linkedDirectories` so each task's worktree gets a junction to the real
   `node_modules` at gate-resolution time.

Three real bugs found in the engine's own generated code, all fixed directly by the
orchestrating session (not via a repair cycle, deliberately, to conserve budget --
each was a small, well-understood, mechanical fix, not a design decision):
1. **ajv/ajv-formats default-import interop under `moduleResolution: NodeNext`.**
   ajv has a usable named export that sidesteps it; ajv-formats does not (its
   `.d.ts` is ESM-authored despite being a CJS package -- a real upstream typing
   mismatch). Fixed with an explicit type assertion on the imported binding.
2. Same class of Windows `.cmd`/`.bat` `spawnSync` problem as #1 above, but inside
   `src/engine/claude-adapter.ts` itself this time (`EINVAL`, not `ENOENT` --
   invoking a `.cmd` executable directly, not npm). Fixed with the same
   `needsShellWrapper()` pattern already proven in `ai-code-worker`.

Real engine-availability incident (not simulated), same as Phase 0: `claude` hit
its actual session rate limit twice during this run (once mid-DAG after 4/5 tasks
had already committed, once again on the retried CLI task). Both times, work
already committed was merged and secured before retrying, and the plan file was
re-trimmed each time so the retry only covered what was actually still needed.
